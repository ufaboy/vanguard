# AGENTS.md — Project Documentation & Engineering Rules

## 1. Core Project Rules (CRITICAL)

- **User balance edits**: The user may change gameplay constants and code directly. Treat current implementation values as the runtime source of truth; documentation and pinned balance expectations may be stale. Preserve unrelated tuning and report mismatches rather than reverting game characteristics to match documentation or tests.

1. **Language Policy (English Source, Localized UI)**:
   - **All source content — UI text, HUD labels, status banners, code comments, identifiers, and documentation — MUST be written in English.** English is the source language and the fallback.
   - **Translations live only in the locale dictionaries**: game UI in `public/src/i18n/locales/<locale>/*.js` (merged by `<locale>.js`) and static pages in `i18n/pages/<locale>.mjs` (keyed by the English text the Astro pages pass to `t()`). Built pages in `dist/site/` are build output. Never hardcode a non-English string anywhere else.
   - **Every new user-facing string goes through i18n**: wrap it in `t('English text', { param })` where it is rendered, or mark catalog / constant strings with `N_('English text')` and translate them on display with `t(value)`. Then add the Spanish entry (`node scripts/i18n-keys.mjs es` lists missing keys; `tests/i18n.test.js` fails until it is added). On the static pages (`site/src/pages/`), wrap text in `t('English text')` and add its translation to `i18n/pages/<locale>/*.mjs`; `pnpm run build:site` (and `pnpm test`) fails on any missing key.
   - **Chat Communication**: Agents may communicate with the user in the user's preferred language in the chat conversation, while keeping all source code and repository files (other than the locale dictionaries) in English.
2. **Pure Vanilla JavaScript Stack (Zero Bundler / No Vite)**:
   - The project is built strictly with **Vanilla JavaScript (Native ES Modules, `.js`)**, **HTML5 (`<script type="importmap">`)**, **Pure CSS (`src/index.css`)**, **Static Dev Server (`pnpm run dev`: builds the site, then serves `dist/site` on port 3000)**, and **Three.js (`three` is the sole runtime dependency)**.
   - **Do NOT use TypeScript (`.ts`, `.tsx`) or React** anywhere in the project.
   - **The game stays bundler-free**: `battlefield.html`, every module in `public/src/`, `public/vendor/` and all game assets are served exactly as written. Never import them through Vite, never add a bundler entry for them, and never add a build step the game needs to run.
   - **Astro (and the Vite it runs on) is allowed only as a build-time generator of the static SEO pages** in `site/` (layout, components and `[...locale]` pages built with `public/` into `dist/site`). Rules there: every `<script>` and `<style>` is `is:inline` so Vite never bundles or rewrites it; no client-side Astro islands or framework components; page behaviour stays in `public/src/pages/*.js` and is loaded as-is; `build.format: 'preserve'` keeps the current URLs (`about.html`, `es/index.html`); assets come from `../public` unchanged; translations still come from `i18n/pages/<locale>.mjs`, and a missing key fails the build. Do not use Vite or Astro for anything else.
3. **Visual & Performance Discipline**:
   - **No CSS `backdrop-filter` / `backdrop-blur`** over the WebGL canvas, as it triggers expensive per-frame framebuffer readbacks. Use high-opacity solid surfaces (e.g., `bg-[#0B0F17]/95`) with crisp borders instead.
   - Maintain support for both hardware-accelerated WebGL and software WebGL fallback (`isSoftwareGl` detection in `TankGameEngine`).
4. **5-Track × 5-Level Player Component System & Standalone Modules**:
   - **Player Tank Components MUST have 5 levels of development (Tiers 1–5)** across all 5 core tracks:
     - **Cannon**: `CANNON_Mk1` to `CANNON_Mk5` (`Cannon Mk1` to `Cannon Mk5`, short Roman `I` to `V`)
     - **Chassis**: `CH1` to `CH5`
     - **Frame**: `F1` to `F5`
     - **Engine**: `E1` to `E5`
     - **Armor**: `A1` to `A5`
   - **Enemy Tank Components**: Enemy tanks may equip both standard player components (`CANNON_Mk1..CANNON_Mk5`, `CH1..CH5`, `F1..F5`, `E1..E5`, `A1..A5`) and enemy-exclusive special components (guns `AUTOCANNON`, `HOWITZER`, `FLAMETHROWER`, `BOSS_DUAL`, `HYDRA_MLRS`, `INFERNO_THERMO`, `NONE`; chassis `CH_HOVER`, `CH_SCOUT`, `CH_TITAN`, `CH_HYDRA`, `CH_INFERNO`, `CH_COLOSSUS`; frames `F_RAM`, `F_TITAN`, `F_HYDRA`, `F_INFERNO`, `F_BASTION`; engines `E_NITRO`, `E_OMEGA`, `E_INFERNO`, `E_SINGULARITY`; armour `A0`, `A_STEALTH`, `A_OMEGA`, `A_HYDRA`, `A_INFERNO`, `A_AEGIS`).
   - **Additional / Optional Modules (`OPTIONAL_EQUIPMENT`)**: Additional modules do **not** have upgrade levels (`leveled: false`); each module is a standalone entity with its own mechanic (`APS_MODULE`, `ROCKET_LAUNCHER`, `REPAIR_KIT_MOD`, `MINE_LAYER`, `WARHEAD`, `JAMMER`, `BUILDER_KIT`, `DOZER_BLADE`, `CLOAK`).
   - **Visibly Distinct 3D Tank Upgrades**: Every tier `1..5` across all 5 tracks (`CANNON_Mk1..CANNON_Mk5`, `CH1..CH5`, `F1..F5`, `E1..E5`, `A1..A5`) and active standalone modules (`APS`, `MISSILE`) must have a clearly visible 3D representation on the player tank rig in `src/game/render/models.js`.
5. **Vehicle Configurations Folder (`public/src/game/vehicles/`)**:
   - All vehicles — **tanks** (`public/src/game/vehicles/tanks.js`), **aircraft** (`public/src/game/vehicles/aircraft.js`), and **drones** (`public/src/game/vehicles/drones.js`) — MUST store their configurations and settings in `public/src/game/vehicles/`.
   - **Ordnance / weapons** (missiles, bombs, mines, artillery shells) are NOT vehicles and remain in `constants.js` / `components/`.
6. **Tank Stats = Type Base + Components + Modules; Models Only Take Guidance From Them**:
   - Every tank type has a **base** (`base: tankBase({...})` in `src/game/vehicles/tanks.js`): its own `hp`, `mass`, per-side `armor` (`front` / `left` / `right` / `rear`), `sightRadius` and `radioAlertRadius`. Core components (`src/game/components/`) and modules add to it. Final stats are computed **only** in `computeTankStats(loadout, base)` (`src/game/constants.js`):
     1. **HP** adds up: `base.hp` + `hpBonus` of every component and module.
     2. **Mass** = `base.mass` + component masses + module masses; **speed** follows only total mass and engine power (no chassis / frame speed multipliers).
     3. **Armour always works per side**: `base.armor[side]` + the armour component (its `armorByAspect`, otherwise its uniform `reductionPct`) + module `armorBonusByAspect`, capped at `DURABILITY.MAX_ARMOR`. Shell hits and blast splash both use the side that is hit; `stats.armor` is the weakest side.
     4. **Damage, penetration and reload** come from the cannon alone.
     5. **Sight and radio** come from the base; modules may add `sightBonus` / `radioBonus`.
   - **Tune a single tank type through its `base`**, never through a stat-only module. `OPTIONAL_EQUIPMENT` holds only equipment with its own mechanic. The balance table (Cannon Mk1 hits per type) is pinned in `tests/tank-stats.test.js`.
   - For 3D models and textures (procedural rigs in `render/models.js` and Blender builds in `assets/blender/`), a component's description is a **recommendation, not a strict specification**. A model may interpret, simplify, or omit a component's suggested visual details as long as the tank stays recognizable and stats are untouched.
   - **Bolt-on attachments are standalone modules, not part of a core component.** Elements such as a dozer blade (`DOZER_BLADE`) belong in `OPTIONAL_EQUIPMENT` and appear on a model only when the tank's loadout lists that module.
6. **Clarify Before Building a Tank Model**:
   - Before creating or rebuilding any tank model (Blender or procedural), **always confirm with the user**: which additional / optional modules the tank carries, its intended size relative to other tanks, and any distinctive features or elements it must (or must not) have.
7. **Release Before Deploy (On `main` After PR Merge)**:
   - Do **not** create Git tags or GitHub releases on a feature/PR branch or prior to PR merge.
   - Only **after** a PR is merged/squashed into `main`, create the annotated Git tag matching the `package.json` version on the resulting squash commit on `main` (e.g., `git tag -a v1.4.1 -m "Release v1.4.1"`) and create the remote/GitHub release with a concise, human-readable **English-only** changelog (matching the `site/src/pages/[...locale]/changelog.astro` entry rather than raw commit messages alone), then run production deploy (`pnpm run deploy`). On Windows PowerShell, always pass `--notes-file -` (or `--body-file -` for PRs) via a single-quoted here-string (`@' ... '@ | gh release create ... --notes-file -`) instead of double-quoted `--notes "..."` so backticks are never interpreted as PowerShell escapes. Do not deploy uncommitted work directly to production without a release.
8. **Version Bump & Changelog Policy (SemVer, Branches & PRs)**:
   - **Patch (`x.y.Z`)**: Bug fixes, removing blocks/elements, or content/code cleanup (`node scripts/bump-version.mjs`).
   - **Minor (`x.Y.0`)**: Adding new functionality or substantially changing existing functionality (`node scripts/bump-version.mjs --minor`, staging `package.json` before committing so `.githooks/pre-commit` preserves the minor bump).
   - **Major (`X.0.0`)**: Never bumped automatically by agents; reserved strictly for the user to update manually in `package.json`.
   - The `.githooks/pre-commit` hook auto-bumps the patch version **only** on direct commits to `main` (it skips feature branches, merges/rebases, and commits where `package.json` version is already staged).
   - While working on a feature branch, do **not** bump the version on intermediate commits. Immediately before creating the Pull Request into `main`, bump the version (`node scripts/bump-version.mjs` or `node scripts/bump-version.mjs --minor`) if it has not already been bumped relative to `main`, and add a concise English changelog entry (`<article class="menu-card">`) for that version at the top of the grid in `site/src/pages/[...locale]/changelog.astro` (English-only page; every string goes through `t()`), without creating any tag or release yet.
9. **Target Platform & Viewport Orientation (Desktop & Landscape Tablets)**:
   - The game UI, HUD, tactical 40×40 isometric arena, and cinematic operations screens are designed exclusively for **Desktop displays and Tablets in Landscape orientation** (16:9 or wider aspect ratio recommended).
   - Mobile phones and portrait orientations are strictly non-target configurations. Layouts, interactive controls, and visual styling must optimize for horizontal widescreen viewing.
10. **Windows PowerShell & UTF-8 File Safety**:
   - Never use PowerShell file cmdlets (`Get-Content`, `Set-Content`, `Out-File`, or `>` / `>>` redirection) to read, modify, or rewrite repository files — Windows PowerShell 5.1 defaults to the system ANSI/UTF-16 codepage and corrupts UTF-8 characters (e.g., `—` → `â€”`) or adds UTF-8 BOMs.
   - Always edit files using dedicated file-editing tools (`edit_file` / `write_file`) or Node.js (`fs.readFileSync(..., 'utf8')` / `fs.writeFileSync(..., 'utf8')`).
   - When running inline Node.js scripts or passing multi-line text to CLI tools (e.g., `gh`) from PowerShell, always pipe a single-quoted here-string (`@' ... '@ | node --input-type=module -`) and use separate lines instead of `&&` (unsupported in PowerShell 5.1).
   - After any bulk edit across multiple files, verify `git diff --stat` and inspect a sample `git diff` to ensure no unrelated characters or encodings were altered.

## 2. Project Overview

**BATTLE TANK** (https://battletank.online; repository and package name `iron-vanguard`, player tank `VANGUARD`) is a free single-player 3D isometric tactical tank game for the browser, inspired by *Battle City*, built with Three.js and Vanilla JavaScript.

### Key Gameplay Features
- **Game Modes**: a 35-mission **Campaign** (*Road to the Capital*) across 7 regions (City outskirts, Forest frontier, Desert crossing, Coastal wetlands, Frozen highlands, Industrial belt, Capital city; missions in `public/maps/campaign/`, briefing data in `src/game/campaign.js`), endless **Survival** maps (`public/maps/survival/`: Iron Crucible, Paris Last Stand) and **Contracts** special operations (`public/maps/contracts/`: the cargo / sabotage raids Blackout Protocol and Last Cargo with `gameMode: "contract"`, plus operation contracts Charles Bridge, Brandenburg Gate, Versailles, Brussels and Remagen Bridgehead that keep their own `gameMode` win rules and are marked by `contractId`; `isContractMap` in `levels.js` covers both, only `gameMode: "contract"` runs the cargo mechanics; campaign missions 1-5 are temporary placeholder maps). Map win rules come from `gameMode` (`extermination`, `stronghold_assault`, `base_defense`; see `src/game/mapRules.js`).
- **40×40 Destructible Isometric Arena**:
  - Tactical grid `GRID_SIZE = 40` (`constants.js` / `levels.js`), `TILE_SIZE = 2`, 1,600 cells per map.
  - Terrain types: Destructible Brick (4 sub-blocks per cell, 4 HP), Hard-to-Destroy Reinforced Concrete (`CONCRETE`, 16 HP; craters open on the faces that were hit and expose the steel rebar), Stealth Forest Canopy, Impassable Water (crossable with the `CH4` All-Terrain or `CH5` Grav-Hover chassis), Low-Friction Ice, and the Command Base HQ. Enemies enter through each map's `enemies.entrances` (there are no spawner pads).
- **Modular Tank Engineering & Physics (`src/game/constants.js`)**:
  - Dynamic calculation of **Total Mass**, **Engine Power-to-Weight Ratio**, **Move Speed**, **Armor Reduction (%)**, **Armor Penetration (%)**, and **Effective Damage**:
    $$\text{EffectiveArmor} = \text{Armor} \times \left(1 - \frac{\text{Penetration}}{100}\right), \quad \text{FinalDamage} = \text{Damage} \times \left(1 - \frac{\text{EffectiveArmor}}{100}\right)$$
  - Player Tier-1 durability is **22 HP** (the player base hull; Tier-1 components add no HP).
  - Low-HP penalty: below 33% HP, movement speed is reduced by 30% and the hull emits damage sparks.
- **5-Track × 5-Level Modular Upgrades with Live 3D Visuals (`src/game/models.js`)**:
  - **Cannon (`CANNON_Mk1`..`CANNON_Mk5` / `Cannon Mk1`..`Cannon Mk5` / `I`..`V`)**: Reload is governed strictly by each cannon's time-based `fireCooldown` in seconds (no active-projectile wait cap). `CANNON_Mk1` / `Cannon Mk1` (`I`) (20 dmg, 0% penetration, 1.5s) $\rightarrow$ `CANNON_Mk2` / `Cannon Mk2` (`II`) with laser rangefinder (22 dmg, 10%, 1.25s) $\rightarrow$ `CANNON_Mk3` / `Cannon Mk3` (`III`) thermal shroud (25 dmg, 22%, 1.2s) $\rightarrow$ `CANNON_Mk4` / `Cannon Mk4` (`IV`) heavy siege gun with hydro-recoil cylinders & rails (28 dmg, 32%, 1.0s) $\rightarrow$ `CANNON_Mk5` / `Cannon Mk5` (`V`) Twin-Linked Heavy AP dual barrels firing a rapid double salvo with 0.2s inter-barrel delay (concrete-cracking 28 dmg, 32% penetration, 1.0s full reload after salvo).
  - **Chassis (`CH1`..`CH5`)**: `CH1` 5-roadwheel steel tracks $\rightarrow$ `CH2` wide chevron treads + blue hydro-shocks $\rightarrow$ `CH3` 7-roadwheel heavy torsion tracks $\rightarrow$ `CH4` Active all-terrain tracks: extra-wide grouser tracks on hydropneumatic struts with gold height adjusters, rear water-jet propulsors, wading snorkel and cyan terrain scanners (crosses water and drives over ice, sand, mud and fords with no slowdown or slip) $\rightarrow$ `CH5` Quad-track articulated bogies + subtle low-profile under-hull hover trim (also all-terrain).
  - **Hull Frame (`F1`..`F5`)**: `F1` welded monocoque + tow shackles $\rightarrow$ `F2` tubular front bull-bar $\rightarrow$ `F3` reinforced heavy frame (front armor beam, side frame rails, corner gussets) $\rightarrow$ `F4` external composite exo-truss roll-cage $\rightarrow$ `F5` Titan serrated siege ram prow + armored sponsons.
  - **Engine (`E1`..`E5`)**: `E1` standard diesel louvers $\rightarrow$ `E2` V8 turbo hood + air filters & side mufflers $\rightarrow$ `E3` V12 twin-intercooler + 4 exhaust stacks + rear fuel drums $\rightarrow$ `E4` gas-turbine nacelle with glowing jet nozzle & intake rotor $\rightarrow$ `E5` Twin-core 225hp fusion reactor domes + dual plasma thrusters.
  - **Armor (`A1`..`A5`)**: `A1` rolled homogeneous hull $\rightarrow$ `A2` bolted appliqué armor + side skirts $\rightarrow$ `A3` *Kontakt-5* ERA wedges + 6 smoke launchers $\rightarrow$ `A4` *Chobham* arrowhead cheeks + roof ERA + rear slat screens $\rightarrow$ `A5` Super-heavy *Relikt* V-glacis citadel + wrap-around reactive pods.
- **Standalone Non-Leveled Modules (`OPTIONAL_EQUIPMENT`)**:
  - **4-Corner Active Protection System (`APS_MODULE`)**: Intercepts Cannon Mk1–Mk3 shells and all missiles for 1 charge each; Cannon Mk4/Mk5, HOWITZER and each BOSS_DUAL shell cost 2 charges. Requires the full charge cost before interception. Cannot stop FLAMETHROWER. Rules live in `public/src/sim/aps.js`.
  - **Turret Homing ATGM Pod (`ROCKET_LAUNCHER`)**: Player-fired guided missiles (`Space` / `Right Click`) with visible warheads on the turret pod.
  - **Emergency Auto-Repair Kit (`REPAIR_KIT_MOD`)**: Automatically restores +20 HP when hull integrity drops below 33%.
  - **Enemy Specialized Modules**: `MINE_LAYER`, `WARHEAD`, `JAMMER` (passive ECM from any living carrier, `public/src/sim/jammer.js`: within 20 cells it hides half of the player's radar contacts and adds false blips; within 5 cells it disables APS interception, blocks ATGM launch and makes in-flight player ATGMs lose lock and fly straight to a point up to 3 cells ahead), `BUILDER_KIT`, `DOZER_BLADE` (front mine-dozer blade, 8 t, no HP bonus), `CLOAK`.
- **12 Enemy Tank Types (`src/game/tanks.js` — `TANK_TYPES` & `TANK_CONFIGS`) + 4 Sector Bosses (`SECTOR_BOSS_CONFIGS`) & Combat Balance**:
  - `SCOUT`, `STANDARD`, `HOWITZER`, `ARMOR`, `SAPPER`, `HOVER`, `KAMIKAZE`, `FLAMETHROWER`, `JAMMER`, `ENGINEER`, `STRIKER`, and `STEALTH`, plus four Sector Bosses (`BOSS_MAMMOTH`, `BOSS_HYDRA`, `BOSS_INFERNO`, `BOSS_TITAN`), each with its own full loadout (there is no shared generic `BOSS` type). Each config's `loadoutSummary` and `base` are the source of truth; HP and armour values are intentionally not listed here because they are tuned often.
  - Sector Bosses are distinct fights. In the Campaign they close regions: Mammoth at mission 15 (and again at 30), Hydra at 20, Cerberus-T at 25, and all four in the mission 35 All-Boss Escalation ending with Titan. `BOSS_MAMMOTH` (`BOSS_DUAL · CH_TITAN · F_TITAN · E_OMEGA · A_OMEGA + ROCKET_LAUNCHER`) is the brawler siege dreadnought: dual siege AP guns, homing ATGM salvos, onboard APS, and a phase shield plus armoured escort at 50% HP. `BOSS_HYDRA` (`HYDRA_MLRS · CH_HYDRA · F_HYDRA · E_OMEGA · A_HYDRA + ROCKET_LAUNCHER`) is an amphibious stand-off rocket-artillery cruiser: it keeps `HYDRA.PREFERRED_MIN_CELLS`..`PREFERRED_MAX_CELLS` away, fires telegraphed 3-rocket triangle salvos at `SALVO_MIN_CELLS`..`SALVO_MAX_CELLS`, answers close intruders with a homing ATGM salvo, and in phase 2 (50% HP) reloads faster and presses closer. `BOSS_INFERNO` / Cerberus-T (`INFERNO_THERMO · CH_INFERNO · F_INFERNO · E_INFERNO · A_INFERNO + DOZER_BLADE, MINE_LAYER, ROCKET_LAUNCHER`) is the thermobaric siege leviathan: 2.5-cell fuel-air shells that turn forest, walls, ice and water into scorched sand, telegraphed overdrive rams through brick, homing ATGMs and mines, and at 50% HP a phase shield, faster weapon cycles and an escort (tuning in `INFERNO`, `constants.js`). `BOSS_TITAN` (`BOSS_DUAL · CH_COLOSSUS · F_BASTION · E_SINGULARITY · A_AEGIS`) is the final super-heavy dreadnought with two independent twin-cannon turrets (4 barrels); Aegis armour is directional (`A_AEGIS.armorByAspect`, judged on the hull) so it must be flanked; at 60% HP it calls a STANDARD + ARMOR escort and at 30% it overloads (faster reload and hull turn, rear armour 0%) (tuning in `TITAN`, `constants.js`).
  - **Enemy Behavior Actions & Luck (`public/src/sim/behavior/actions.js`)**: every enemy and boss config in `tanks.js` declares its own `behavior: defineBehavior(role, actions)`. `actions` is an ordered priority list; whenever the tank needs a movement order, a shot or a special, it takes the FIRST listed action of that kind whose condition holds. Each action has its own `luck` in `[0, 1]`: a plain success probability rolled once when the action is assigned. Move actions: `move_to_player` (success: the role brain fights the known player), `move_to_player_base` (drive into firing range of the HQ and hold), `defend_enemy_base` (return next to the enemy base while the player is within `DEFEND_TRIGGER_CELLS`), `move_to_zone` (`zone: { row, col }`), `follow_route` (the encounter's map `patrolRoute`, once), `patrol_zone` (around the given or current zone), `take_cover` (available for `afterHitSec` after a hit, default 3 s, or below the optional `hpBelow` HP ratio: drive to the nearest cell hidden from the player and hold it for `COVER_HOLD_SEC`), `ambush` (hide 3-6 cells from the last known player position, else from the HQ, preferring forest, chokepoints and the player's trail; hold until the player comes within `triggerCells`, default 5, then the next action springs the trap); cover and ambush orders stay active until they end even when their trigger has passed; a failed move roll drives to a random cell in another zone. The 40×40 arena is split into 6×6-cell zones (`ACTION_TUNING.ZONE_CELLS`). Orders are re-rolled when they end, after `MOVE_PLAN_SEC` (failed: `FAILED_MOVE_SEC`), or when a higher-priority action becomes available. Shoot actions: `shoot_player`, `shoot_player_base`, `shoot_obstacle`, `shoot_random`; rolled per shot: a hit aims exactly at the target's current position, a miss aims deliberately beside it (indirect fire lands outside the splash circle; a missed missile never homes). Specials: `set_mine` (miss: the mine lands off the planned spot), `build_brick`, `repair_ally`; unlisted specials always succeed. Luck values come only from the tank config (no map-level scaling, no spawn jitter); difficulty is tuned through enemy composition and count. Crew timing (reaction, turret alignment, reload jitter) is the same for every enemy (`GUNNER` in `gunner.js`). Per-tank weapon settings next to `behavior`: `artillery: { aimSec, flightSec }` (indirect fire: aiming time before each shell and shell flight time; defaults `ARTILLERY.AIM_TIME` / `FLIGHT_TIME`) and `missile: { homing }` (whether enemy missiles steer after launch).
  - **Enemy Role Brains (`brain.js`, `ROLE_CONFIGS`)**: every enemy tank type declares a `behavior.role` in `tanks.js`. The brain controls movement during a successful `move_to_player` order, which is available while the enemy sees the player or remembers / was radioed the player's position (artillery and jammer also while any ally spots the player; the engineer also while an ally needs repair). Brains pick a tactic, choose a tactical cell (`findTacticalCells`: distance band, LOS rule, cover, forest, water, chokepoints, player trail, flank direction, squad bearing slot, ally crowding, small score noise) and follow an A* path to it. Roles: `line` (`STANDARD`: engage from a firing cell, duck into cover, peek again; retreats once below 35% HP), `flanker` (`SCOUT`, armed with `AUTOCANNON`: 6-10 cells on the player's rear side, kites when crowded, evades after hits), `spearhead` (`ARMOR`: closes to 2-4 cells and holds glacis-first), `artillery` (`HOWITZER`: hidden 7-11 cell firing cell, fires on spotter data, relocates after 2-3 barrages, flees threats closer than 5 cells), `minelayer` (`SAPPER`: mines chokepoints on the player's recent trail, mines while evading, fights as `line` once out of mines; on patrol it only mines cells the player drove through), `raider` (`HOVER`: strikes from water / shorelines the player cannot cross, then withdraws), `hunter` (`KAMIKAZE`: stalks through cells hidden from the player, then a telegraphed red-spark zigzag charge inside 5 cells), `ambusher` (`FLAMETHROWER`: lurks hidden 3-6 cells away in forest / corners, rushes inside 5 cells), `ewar` (`JAMMER`: shadows out of sight, closes to 3-5 cells for a timed screening run while allies are engaged, then withdraws out of sight and repeats; its ECM is passive, see `sim/jammer.js`), `support` (`ENGINEER`: drives next to the most damaged ally, otherwise fortifies, flees close threats), `standoff` (`STRIKER`: 7-10 cell LOS launch cell, shifts sideways after launches), `sniper` (`STEALTH`: 8-11 cell overwatch, one shot then slips into a hidden cell; standing still gives full camouflage). Sector Bosses use the same framework with their scripted weapons and phases intact: `dreadnought` (`BOSS_MAMMOTH`: closes to 3-6 cells and side-steps every other cycle), `cruiser` (`BOSS_HYDRA`: strafes inside its `HYDRA.PREFERRED_MIN_CELLS`..`PREFERRED_MAX_CELLS` band, capped inside sight range; phase 2 presses into `SALVO_MIN_CELLS`..`PREFERRED_MIN_CELLS`), `juggernaut` (`BOSS_INFERNO`: presses into 3-7 cells and shifts flank every cycle), `fortress` (`BOSS_TITAN`: advances glacis-first to `TITAN.HOLD_DISTANCE_CELLS` and holds). Boss bands are passed from `constants.js` via `bossBrainOverrides` in the engine (`src/game/engine/`). Without contact or memory the next movement action of the behavior applies (`follow_route`, `move_to_player_base`, `patrol_zone`, ...).
  - **Enemy Abilities (`src/game/abilities/`)**: special mechanics are plugged into a tank type from its config, next to its role: `behavior` says *how* a tank fights, `abilities` says *what is special* about it (e.g. `SAPPER`: `behavior: defineBehavior('minelayer', [...]), abilities: ['mineLayer']`; specials roll their action luck via `rollTankSpecial`). Each ability is a module with `id` and optional hooks: `init(tank, game)` at spawn; `tryUse(tank, game, { brainActive, canSeePlayer })` for the shared `specialCooldown` slot (returns a cooldown when it acts; run by `updateAbilities`); `fire(tank, game, { target, distToPlayer, aimReady, token })` to replace the main gun (`target` is `player`, `base`, `breach` or `terrain`; returns the reload or 0 to hold fire; run by `fireAbilityWeapon`); `unarmed: true` for tanks without a gun (no aiming, no attack token; the engine checks `tank.armed`); and `contactRange` + `onContact(tank, game)` for effects when the tank touches the player (returning true spends the tank; run by `spendContactEnemy`). `equipAbilities` resolves them at spawn and caches `tank.armed`, `tank.weaponAbility` and `tank.contactAbility`. Abilities keep their own decision logic and tuning constants and use the engine only for world services. Current abilities: `mineLayer` (`MINE_LAYER`: ammunition from the `MINE_LAYER` module), `engineerSupport` (`ENGINEER_SUPPORT`: weld allies, repair bricks, raise walls), `flameStream` (`FLAMETHROWER`: napalm puffs tuned by `FLAME_STREAM`; burns walls and terrain at half rate, never targets the base), `contactWarhead` (`KAMIKAZE`: unarmed, detonates `KAMIKAZE_BLAST` inside `CONTACT_WARHEAD.TRIGGER_RANGE`). New special mechanics go here as abilities, not as `enemyClass` branches in the engine; unknown ability ids throw at spawn and in `tests/enemy-abilities.test.js`.
  - **AI Telemetry Overlay (F3)**: `aiDebugMode` shows exact HP bars plus a floating label per enemy (role, tactic, `FIRE` while it holds an attack token, the current movement order and shot with their dice results) and its remaining A* path (or a line to the player during a direct charge). Built in `updateAiDebugOverlay` only while the mode is on and fully disposed when it is turned off.
  - **Squad Director (`squad.js`)**: at most `maxAttackers` enemies (map JSON `enemies.maxAttackers`, default 3) may shoot at the player at once; tokens go to the closest tanks and rotate after 4 s when others wait. Bosses are exempt. Fighting tanks also get evenly spread bearing slots around the player so they converge from different sides. Artillery fires on spotter data while any ally sees the player.
  - **No-lead rule**: enemies never lead their shots. The Gunner (`gunner.js`, `computeAimPoint`) only reads the target's current position; do not add target velocity to enemy aiming. Homing missiles and artillery striking the current position are not leading.
  - Hits-to-kill and directional durability depend on the current tank base, equipped components, hit aspect and cannon. Compute them from `computeTankStats` and the combat damage functions. Historical numeric expectations in tests or documentation may lag user tuning; never revert current stats just to match an old snapshot.
- **Surfaces & Obstacles Catalog (`src/game/terrains/surfaces.js` — `TileType`, `SURFACE_TYPES`, `SURFACE_CONFIGS`)**:
  - Dedicated specs and descriptions for every tile type (`EMPTY`, `ROAD`, `GRASS`, `STONE`, `SAND`, `WATER`, `ICE`, `SWAMP`, `OIL_SLICK`, `BRICK`, `CONCRETE`, `FOREST`, `BASE`, ...).
- **Layered Terrain (`src/game/terrains/layers.js`)**:
  - Every cell has a flat `surface` (`EMPTY`/ground, `ROAD`, `GRASS`, `STONE`, `SAND`, `WATER`, `ICE`, `SWAMP`, `OIL_SLICK`) and an optional `object` (decoration, facility or wall). `cell.type` is the top layer (`object ?? surface`) and is what gameplay code reads.
  - Change a cell at runtime only through `setCellObject` / `setCellSurface`; never write `cell.type` directly, or the next `syncCellType` restores the stale layer.
  - `SURFACE_CONFIGS` is the single source for driving rules: `isTilePassable` (collision, A* navigation, entry routes) reads `passableByTracks`, and `cellMovement` / `combineCellMovement` multiply the speed / accel / turn / brake multipliers of both layers for player and enemy movement (a crater on a road keeps part of the road bonus). `maxSpeedCells` caps top speed in cells per second instead of scaling it (`STONE`: 1.5). All-terrain and hover chassis keep bonuses but ignore penalties and caps, except `affectsAllTerrain` (rubble); `playerOnlyTraction` (ice) does not slow enemies. Results are cached and frozen. Water speed stays per chassis in the movement code. Tune terrain traction in the catalog, not in the controllers.
  - Maps use `surfaceLayout` (`G`/`.` ground, `R` road, `W` water, `I` ice, `S`/`N` sand, `^` stone, `V` grass, `M` swamp, `L` oil) plus `objectLayout` (`B` brick, `C` concrete, `F` forest, `X`/`Z` hedgehog, `D`/`O` barrel, `Q` boxes, `K` crater, `T` water tower, `=` bridge, `U` rubble, `A`/`P` houses, `H` HQ, `E` enemy base). `canPlaceOnSurface` defines which objects may stand on which surfaces.
- **5 Tactical Field Power-Ups (`src/game/powerups.js` — `POWERUP` & `POWERUP_TYPES`)**:
  - `REPAIR`, `EMP`, `BASE_RESTORE`, `APS`, and `MISSILE`. Field Power-Ups are strictly situational combat abilities.
  - **BOX Supply Rules**: Tanks award credits; fully opened BOX caches roll `BOX_POWERUP_DROP_CHANCE` (currently 33%). Successful drops draw from the match's shuffled pool without replacement; exhausted pools reshuffle without adjacent repeats. Pickups stay at the cache location until collected or the mission ends. `BASE_RESTORE` has priority while HQ is destroyed and no reconstruction pickup is pending; emergency priority may override the bag cycle. Legacy map pickup types do not predetermine BOX contents.
  - **Hangar Supplies and Repairs**: Buy one APS charge for `APS.CHARGE_CREDIT_PRICE` (currently 1000) or one missile for `MISSILE.CREDIT_PRICE` (currently 3000), up to their current capacity limits. Component repair is priced by purchased tier through `componentRepairCost`: II 600, III 900, IV 1200, V 1500 credits; Tier I cannot currently fault.
  - **Credit Economy & Hangar Upgrades**: Destroying enemies and clearing missions yields **Credits ($)**. Upgrading core tracks (`CANNON_Mk1..CANNON_Mk5`, `CH1..CH5`, `F1..F5`, `E1..E5`, `A1..A5`) is performed in the **Hangar (`[U]`, shown in the UI as the Garage; `src/hangar-ui.js`)** accessible within the repair radius of the Allied Command Base (or from the menu). Entering the Hangar in combat pauses battlefield simulation.
  - **Fortified Allied Base**: The player's Command Base is a two-bay tank workshop (`createCommandBaseBlock` in `render/models.js`) that occupies 2×1 cells (`baseCell` + its right neighbour) on the outermost row. Every map authors its own HQ cover in `objectLayout`: a 4-cell line of reinforced Concrete (16 HP) two rows towards the enemy, with the lane between it and the HQ and the cells beside the HQ left open so tanks can drive up to it. The loader never adds walls or clears cells around the HQ (only the map file decides the terrain); `getBaseLayout` (`levels.js`) only describes the HQ footprint and where the cover row sits, and the Survival boss-wave reward restores only the cells the map authored as concrete. Either HQ cell being hit destroys the base.
  - **Victory Cinematics (`VICTORY_CINEMATICS`, `constants.js`)**: `triggerMissionVictory(banner, focusTarget)` sets `GameStatus.VICTORY` immediately (rewards, medals and stats settle at once) but holds the results modal for `DURATION_SEC` (`victoryCinematicsTimer`, `hud.victoryCinematicsActive`). The camera (`InputCameraController.updateCamera`) focuses the final destroyed tank or enemy HQ, pushes in (`ZOOM_FACTOR`) and orbits 360°; the target is removed from `engine.enemies` right away but its model/tile explosion (`onDetonate`) fires `DETONATE_DELAY_SEC` into the orbit. Contract extraction has no target and orbits the player. Zoom changes go through `engine.updateCameraProjection()` (camera bounds only); `handleResize()` is reserved for real viewport resizes because it resizes the renderer.
  - **Missile FPV Chase Camera (`MISSILE.FPV_*`, `constants.js`)**: optional (`V`, HUD `FPV [V]` button, Settings toggle; saved as `missileFpvEnabled`). While a player ATGM is in flight the engine renders `fpvCamera` (perspective) trailing the missile, runs the simulation at `MISSILE.FPV_TIME_SCALE` (`getTimeScale()`) and, after impact, holds the view for `FPV_POST_EXPLOSION_DELAY` before returning to the isometric camera. Mouse aim updates are paused while it is active. Tune every distance, height, smoothing and FOV value in `MISSILE.FPV_*`, never inline.
  - **Alloys & Part Levels Removed**: Secondary Alloys and Lv.0 → Lv.3 sub-levels are deleted; Credits are the sole universal upgrade currency.

## 4. Development & Verification Workflow

- **Adding/Editing Features**:
  - Keep state management decoupled: `TankGameEngine` (`public/src/game/engine/engineCore.js`, with subsystems split into sibling modules in `engine/`) owns the 3D scene and simulation state and emits HUD snapshots to `public/src/main.js` through the callback passed to its constructor.
  - Use DOM event delegation (`data-action` attributes) for UI interactions (`public/src/main.js` on the battlefield page, `public/src/pages/*.js` and `src/app/shell.js` on the static pages).
  - **Static pages are the SEO surface**: every out-of-combat page (`site/src/pages/[...locale]/index.astro`, `campaign.astro`, `how-to-play.astro`, ...) ships its full text, meta tags and JSON-LD in static HTML rendered at build time. Page props set title, descriptions, image and JSON-LD; `PageLayout.astro` writes the head and footer once for every page. Keep visible copy, `<title>`, `meta description`, Open Graph / Twitter tags and JSON-LD consistent with each other and with the current game facts. `battlefield.html` is `noindex`; contracts open directly as `battlefield?mode=contract&id=<contract id>`. The home JSON-LD `softwareVersion` is read from `package.json` at build time; `scripts/deploy.mjs` syncs sitemap `<lastmod>` dates from the last commit of each page's sources.
  - **Localization (i18n)**: the battlefield UI is localized at runtime by `public/src/i18n/index.js` (gettext style: the English text is the key). `battlefield.html` has `<html data-locale="auto">`: it uses `?lang=`, then the saved preference (`iron_vanguard_locale_v1`), then the browser language. Static pages use their `<html lang>`; pages with hreflang alternates save it as the preference. The Settings modal has a Language row (reloads, or opens the translated twin). Extra locales are `es`, `pt-BR` (`/pt-br/`), `de`, and `fr`. Pages listed in `LOCALIZED_SLUGS` (`site/src/i18n/index.js`) are built in English and every extra locale (`/about`, `/es/about`, `/pt-br/about`, `/de/about`, `/fr/about`); they carry `hreflang` alternates (`en`, `es`, `pt-BR`, `de`, `fr`, `x-default`) and `og:locale`, are listed in `sitemap.xml`, and their links point to the active locale's twins where they exist, otherwise to the English pages (`localHref`). Every other static page (changelog) stays English-only.
- **Verification**:
  - Always run `compile_applet` (`pnpm run build`: lint + Astro build) and `lint_applet` (`pnpm run lint`) after making code changes to verify zero build or syntax errors. Lint also fails on calls to missing methods and on unused code: delete what it reports, or drop the needless `export`, instead of silencing it.
- **Blender Builds (`assets/blender/`)**:
  - Always pass an **absolute** output directory inside `assets/blender/<tank>/` after `--` (e.g. `-- C:/projects/.../assets/blender/armor`). On Windows, Blender resolves relative image/render paths against the drive root, so a relative path like `-- armor` writes to `C:\armor\`. The build and bake scripts refuse any output directory outside `assets/blender/`.
